# 0. 真实场景：7000 行、149 个文件

我把 Agent V1 的执行文档扔给 Codex，回来一看：好家伙，一口气改了 7000 行、149 个文件。

（之前标题写的是“糊了 7000 行”，本意是夸它干活猛，不是说它糊弄。现已为受害 Codex 恢复名誉。（笑））

这种量级，逐行硬看不现实：看到第 30 个文件，注意力已经散了，最后变成“看起来都挺对”。所以我把原来那套 SOP 按这次的经验重新排了一下——**不是从第一行看到最后一行，而是分层看，每一层只回答一个问题。**

另外，AI 能帮忙写代码之后，我给自己卡的尺度是两条：

1. 代码可以 AI 写，**测试我自己来写**（至少关键路径的测试由我定义）。
2. **业务边界我来划**，AI 在边界里干活。

下面每一层，其实都是在检查这两条有没有守住。

# 1. 第一层：施工验收（先别急着 Code Review）

先当包工头验收，不当 reviewer。这一层只看“活干没干完、有没有干出界”。

- **改了哪些文件**：`git diff --stat` 过一遍，按模块分组，心里先有张地图。
- **有没有越界修改**：执行文档没让动的模块、配置、公共工具类，被顺手改了没有？
- **有没有遗漏**：文档要求的文件、接口、迁移脚本，是不是都在？
- **有没有意外生成物**：临时文件、调试输出、IDE 目录、大段被注释掉的代码。
- **能不能跑**：编译、启动、跑现有测试。跑不起来的东西不配进入下一层。

这一层不通过，直接打回，不浪费后面的注意力。

# 2. 第二层：架构与业务边界

对着总纲（设计文档 / 执行文档）看，重点不是代码写得漂不漂亮，而是**是不是按图施工**。

- **是否符合总纲**：分层有没有被打穿？该走领域服务的，是不是直接操作了 Mapper？
- **接口契约**：入参、出参、错误码、幂等语义，和文档对得上吗？
- **状态机**：状态迁移是否只走允许的边，非法迁移是否被拒绝。**重点看测试，不要只看实现**——实现可以写得很像对的，测试才说明它到底覆盖了什么。
- **事务与并发**：事务边界在哪里？条件更新、锁、重试是不是和设计一致？

# 3. 第三层：恢复与权限

这一层是 Agent 项目特有的重点，也是最容易“看起来能跑、实际上不安全”的地方。

- **durable recovery**：进程挂了、请求超时了、做到一半断了，重启之后能不能从持久化的状态恢复？会不会重复执行？
- **`Evidence → Assessment → Permission`**：事实、判断、授权三层有没有混在一起？有没有“判断出来了，就顺手执行了”的捷径？
- **Agent Loop**：循环有没有上限？失败怎么退出？模型输出不合法时是不是 fail-closed？
- **Human Review**：需要人工确认的动作，是不是真的会停下来等人，而不是记一条日志就继续？
- **真正的业务执行权限**：最终执行动作之前，权限是不是由确定性代码校验，而不是由模型说了算？

相关文章：[确定性 Agent 架构](/posts/deterministic-agent-architecture)、[Agent V0 边界设计札记](/posts/agent-v0-boundary-notes)。

# 4. 第四层：普通代码质量

最后才看这一层，而且这一层最适合交给 Codex 自己审：

- 潜在 NPE、边界条件、分支遗漏
- 资源泄漏、并发问题
- 异常处理与日志：异常是不是被吞了？日志有没有带上足够的上下文、有没有泄漏敏感字段？
- SQL / 缓存误用、未处理的失败路径
- 可读性、命名、明显的拼写错误

之所以放最后：前三层有问题，这一层改得再干净也白改。

# 5. 一份可复制的 Codex Review Prompt

之前有一次 token 存错了，我测了一下午没找到，Codex 花了 2 分钟就审出来，顺手打了补丁（这个坑记在 [Java 小事故复盘](/posts/java-small-incidents-review)）。后来我发现，让 Codex 审代码，这几件事写清楚，效果差别很大：

```markdown
## 角色
你是一个资深后端 reviewer。

## 审核范围
- 文件：xxx/XxxService.java、xxx/XxxMapper.xml
- 方法：XxxService#doSomething

## 设计目标
（从接口文档 / 设计文档里 copy：这个方法要做什么、约束是什么）

## 工程约束
- 技术栈：Spring Boot + MyBatis + Redis
- 项目特别用法：Redis 统一用 StringRedisTemplate
- 返回结构：统一 Result<T>
- 改动风格：尽量最小改动，不要重写整个类

## 输出要求
1. 按优先级列出问题（P0 必须改 / P1 应该改 / P2 可选），每条说明「不改会发生什么事故」
2. 给最小补丁（diff 风格）
3. 给可复现的回归用例
4. 额外需要指出的问题

## 减少幻觉
如果无法从代码中判断某个常量、错误码、字段含义，请标注为假设点，不要自行编造。
```

最后一条最重要：**不确定就让它标假设，而不是猜完直接改。**

# 6. 修复 → 复验 → 归档闭环

## 6.1 流程

1. **写代码 → 本地跑最小门槛**：formatter / lint / 静态检查（能自动化就自动化）；单测至少覆盖新增和改动路径。
2. **Codex code-level review → 产出报告**：报告放到 `docs/codex-reviews/`，按日期 + 模块命名，例如 `2026-02-08-login-token.md`。
3. **按报告改 → 再跑测试**：配一个勾选清单，避免改着改着把主线改丢。
4. **Thinking 模型做第二层 review**：接口契约、幂等、降级、限流、可观测性、缓存一致性、事务边界、并发与重试策略、数据增长后的性能拐点、最容易上线炸的路径。
5. **压测与文档收尾**：压测不是跑一下，而是场景、数据规模、并发模型、指标口径、瓶颈定位、结论与改动建议；文档写模块介绍、接口文档、关键设计决策（为什么这么做，不那么做）。

## 6.2 报告模板（`docs/codex-reviews/`）

- 变更摘要
- Codex 发现
  - P0：问题 / 影响 / 建议修改点（指到文件 + 函数）
  - P1：...
  - P2：...
- 已处理清单（checkbox）
- 遗留项（明确说明为什么不改 + 风险说明）

## 6.3 压测文档最小模板

- 环境：机器、JVM 参数、DB / Redis 规格、版本
- 场景：接口、数据量、并发、持续时间、思考时间
- 指标：P50 / P95 / P99、吞吐、错误率、CPU / GC / DB 慢查询
- 结论：瓶颈点 & 下一步优化路线

## 6.4 自动化链路

- PR 自动跑：lint + test + 静态扫描（SpotBugs / Checkstyle / Semgrep 之类）

# 7. 小改动和大改动，分别走什么流程

每次都走全链路会把人拖死，所以分两档：

| 改动类型 | 流程 | 是否落文档 |
|---|---|---|
| 小改动（单方法修复、小重构） | 本地检查 → 小范围 Codex review → 测试 | 不落，只留在 PR 描述或临时 notes |
| 大改动（新模块、关键重构、AI 大批量生成） | 四层审核 → Codex 报告 → 修复复验 → 压测 / 文档 | 落到 `docs/codex-reviews/` |

需要固化到 repo 的只有：新模块完成、关键重构、性能优化前后、上线前检查。

# 8. 这套设计的好处和风险

## 好处

- **降低心理摩擦**：不需要每次凭意志力相信自己对还是错，而是把信任交给流程，流程跑完，人就安心。
- **可复盘、可证明**：`docs/codex-reviews/` + 压测文档，是一条工程能力的证据链。
- **把注意力分层**：Codex 抓底层 bug（拼写、分支遗漏、NPE、资源关闭、日志），人和 Thinking 模型抓系统性炸点（幂等、重试风暴、缓存击穿、慢 SQL、错误码契约、权限边界）。
- **形成模块闭环**：不是一直写，而是交付一个个完成态的模块。

## 风险

1. **文档负债**：每次 review 都提交报告，很快会被文档淹死。→ 只在上面那几种情况落文档。
2. **报告噪音与形式主义**：Codex 容易给一堆看起来很对但不关键的建议。→ 强制 P0 / P1 / P2 分级。
3. **泄漏风险**：review 文档进 repo，容易带上内部 URL、token、真实数据样例、敏感字段。→ 模板里加一条：不得出现真实密钥 / 真实用户数据 / 完整链接串，样例一律脱敏。
4. **节奏变慢**：每个模块看起来更慢，但这是返工减少的慢。→ 小改动走轻量链路。

# 旁注：Codex App

顺带夸一下 Codex App，比之前的 terminal 端方便多了：UI 更清晰，可以轻松回溯某个项目的会话；改动之后能直接定位到项目文件；可以编辑 skills；默认跑在沙盒里，不给权限不会动项目文件。
